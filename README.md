## 一、项目背景

真实运维场景里,应用日志分散在多台服务器上,出故障时只能靠人肉翻日志:

- 想知道「刚才哪个接口变慢了」→ 得一台台机器登上去 `grep`;
- 想知道「今天的错误率比昨天高多少」→ 没有现成的聚合数据;
- 出故障后排查根因 → 靠经验猜,而且每次都要重新走一遍。

**LogSentinel 把这条链路自动化**:
采集 → 结构化 → 聚合指标 → 检测异常 → 告警 → AI 分析根因。

## 二、功能特性

| 模块 | 能力 |
|---|---|
| **日志采集** | HTTP 批量上报接口,单次最多 1000 条;单请求体积上限保护 |
| **数仓分层** | ODS(原始)→ DWD(结构化)→ ADS(指标),共 7 张表 |
| **数据质量** | 解析失败写入**死信表**并计数,**不中断主流程** |
| **指标聚合** | 按「分钟 + 接口」计算 QPS / 错误率 / P95 / 平均延迟 |
| **异常检测** | **动态基线**(近 60 分钟中位数)+ **绝对阈值**双条件判定 |
| **告警闭环** | 异常 → 告警 → 值班确认(ack)状态流转 |
| **AI 根因分析** | 基于**证据**的 LLM 诊断,输出结论/原因/排查步骤/处置建议 |
| **成本控制** | 诊断结果落库缓存,同一异常不重复调用模型 |
| **优雅降级** | 未配置 API Key 或调用失败时,**自动切换规则引擎** |
| **可观测性** | 健康探针(探数据库)、结构化日志、每分钟定时调度 |
| **定时任务** | APScheduler 每分钟自动跑「解析 → 聚合 → 检测」 |

## 七、设计要点

> 这一节是项目的技术核心,也是面试最常被追问的部分。

### 1. 为什么做数仓分层?

- **ODS 层原样存储**:解析逻辑一旦有 bug,可以直接拿原始日志**重跑**,不必回源头重新采集;
- **DWD 层存结构化字段**:后续所有查询和聚合都基于它,不用反复解析文本;
- **ADS 层存预聚合结果**:看板查的是算好的分钟级指标,**不用每次扫全表**。

### 2. 如何保证任务幂等?

同一任务执行一次和执行多次,结果必须一致。本项目用了两种方案:

| 环节 | 方案 | 实现 |
|---|---|---|
| 解析任务 | **标记位(水位线)** | 只处理 `parsed=False` 的记录,处理完立即置 `True` |
| 聚合任务 | **分区覆盖写** | 先按分钟分区删除,再整体插入 |

**为什么重要**:任务跑到一半机器重启、运维手动重跑补数据、调度超时自动重试 ——
这些场景下,**不幂等会导致数据重复,报表数字直接失真**。

### 3. 如何处理脏数据?

解析失败的日志**不抛异常中断任务**,而是:

1. 写入 `ods_log_dead_letter`(死信表)留档;
2. 主流程继续处理后续正常数据;
3. 日志计数告警,便于及时发现上游格式变更。

> **关键点**:如果坏数据直接中断管道,一条格式异常的日志就能堵死后面几万条正常数据;
> 如果静默丢弃,你永远不知道丢了多少。**死信表是两者的平衡点。**

### 4. 为什么用 P95 而不是平均值?

| 场景 | 平均值 | P95 |
|---|---|---|
| 95 个请求 20ms + 5 个请求 5000ms | 269ms(看起来还行) | 269ms |
| 90 个请求 20ms + 10 个请求 5000ms | 518ms | **5000ms** |

**平均值会被长尾掩盖**:如果 99 个用户 20ms、1 个用户 3 秒,平均值只有 50ms,
但那个用户已经炸了。**P95 回答的是"最慢的 5% 用户体验有多差"。**

### 5. 异常检测:动态基线 + 绝对阈值

```
异常判定 = 当前值 > 基线 × 倍数阈值  且  当前值 > 绝对地板
基线     = 该接口最近 60 分钟该指标的中位数
```

**为什么要用中位数而不是平均值**:平均值会被历史故障值污染 ——
一次 5000ms 的故障会把基线抬高,导致**下次同样规模的故障反而不超标**(漏报)。
中位数是稳健统计量,对极端值不敏感。

**为什么要有绝对地板**:如果某接口基线是 0.0001,「超过基线 2 倍」= 0.0002,
依然可以忽略。加上绝对地板(错误率 > 5%、P95 > 200ms)才能真正过滤误报。

**⚠️ 一个真实的漏报修复**:基线为 0(历史上从没出过错)时,
倍数无法计算。初版代码直接 `continue` 跳过了判定 ——
结果**错误率从 0% 暴涨到 100% 却不告警**。

修复方案:**基线为 0 时退化到绝对阈值判定**。
因为告警的目的是"发现异常",倍数只是手段;手段失效时应换一个,而不是放弃判断。

> **监控系统最危险的失效不是误报(吵),而是漏报(静默)。**

### 6. AI 根因分析:证据优先 + 降级设计

**错误做法**:把"接口报错了"直接丢给模型 → 它会编(幻觉)。

**本项目的做法**:由代码收集证据,模型只负责推理。

| 步骤 | 谁做 | 内容 |
|---|---|---|
| 收集证据 | **代码** | 该接口近 10 分钟指标序列 + 异常时段日志样本(按状态码、耗时排序取 Top12) |
| 推理归因 | **LLM** | 综合证据推断最可能原因 |
| 输出动作 | **LLM** | 给出可执行的排查步骤和处置建议 |

**Prompt 的三条约束**:① 不得编造未提供的信息;② 证据不足要明确说"需进一步确认";
③ 必须按固定结构输出(结论/原因/排查步骤/处置建议)。

**成本与容错**:

- `max_tokens=900` 限制输出长度;
- `ai_diagnosis` 表缓存结果,**同一异常不重复调用**;
- 未配置 Key 或调用失败时,**自动降级为规则引擎**,服务永远可用。

## 九、Docker

```bash
docker compose up --build
```

容器启动时会自动执行 `scripts/seed_demo.py` 灌入演示数据,保证看板开箱即有内容。

**镜像设计要点**:

| 做法 | 原因 |
|---|---|
| 先 `COPY requirements.txt` 再 `COPY . .` | 利用 Docker **层缓存**,改业务代码不用重装依赖 |
| `PYTHONUNBUFFERED=1` | 保证 `docker logs` 能实时看到日志 |
| `TZ=Asia/Shanghai` | 容器默认 UTC,不设会导致所有时间差 8 小时 |
| `--host 0.0.0.0` | 只监听 `127.0.0.1` 的话,容器外部访问不到 |
| `${PORT:-8000}` | 云平台会动态注入 PORT |
| `.dockerignore` 排除 `.env` / `.venv` / `data` | 防止密钥进镜像、镜像体积膨胀 |
